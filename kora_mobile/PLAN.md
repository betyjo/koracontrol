# Kora Control — Mobile App (Flutter)

A Flutter mobile application that mirrors the Kora Control web customer dashboard,
enabling individual users to monitor water usage, check water quality, view billing
history, make payments, receive real-time alerts, and control their water valve
remotely.

> **Status:** Initial setup + foundation. Feature modules are scaffolded with working
> data layer; UI implementation continues iteratively.

---

## 1. Goals & Non-Goals

### Goals
- Deliver a **customer-facing** mobile app (CUSTOMER role from the web app).
- Mirror every customer-accessible feature of the web dashboard in `kora_frontend`.
- Reuse the **existing Django REST backend** (`kora_backend`) — no backend rewrite
  is required for ~95% of features. The mobile app consumes the same `/api/*`
  endpoints the web app uses.
- Single codebase, ships to **iOS, Android, Web** (Flutter web), with a focus on
  iOS + Android for the first release.
- Modern, clean UI matching the web's visual language: blue/indigo gradient,
  slate neutral palette, light + dark mode, rounded-2xl/3xl cards.

### Non-Goals (v1)
- Operator/Admin role workflows (these remain web-only for v1).
- Real-time push (FCM/APNS) — v1 uses **polling** like the web app, with the
  data layer designed so a push channel can drop in later.
- Offline-first architecture — v1 requires connectivity for live data; cached
  reads are best-effort.

### State management
- **Provider** (already battle-tested, lightweight, matches the simplicity of the
  web app's approach). Each feature has a `*_controller.dart` exposing
  `ChangeNotifier`.
- **go_router** for navigation, with an auth-guard redirect.

### HTTP
- **dio** for HTTP (interceptors for JWT, refresh-on-401, retry).
- **flutter_secure_storage** for token persistence.
- Polling-based "real-time" (matches web): `Timer.periodic` at 5s for the home
  screen and 30s for alarms/notifications. Each controller owns its own timer.

### Charts
- **fl_chart** — used for usage, cost, water quality, and live flow line.

### Payments
- **webview_flutter** + **url_launcher** for the Chapa hosted checkout (matches
  the web app's flow where the customer is redirected to a Chapa URL and then
  the callback hits the backend).

### Storage
- **flutter_secure_storage** for JWT.
- **shared_preferences** for non-sensitive preferences (theme mode, last-seen
  notifications).

## 5. Auth Flow

Mirrors the web app:

1. **Login** — `POST /api/auth/login/` returns `{access, refresh, user}`.
   Tokens stored in flutter_secure_storage. User role parsed from JWT
   (`user_role` claim) for guarding routes.
2. **Register** — `POST /api/auth/register/`, then auto-login.
3. **Forgot password** — `POST /api/auth/forgot-password/` with email.
4. **Reset password** — `POST /api/auth/reset-password/` with token + new pwd.
5. **Token refresh** — Dio interceptor calls `/api/auth/refresh/` on 401.
6. **Logout** — local token clear + go_router redirect to `/login`.

A 401 anywhere triggers: clear tokens → navigate to `/login` with a
`sessionExpired=true` query param (matches web's `sessionStorage` toast pattern).

## 6. Valve Control (Mobile-only Feature)

The web app's valve/setpoint endpoints are operator-only. The mobile app needs
a **customer-scoped** valve toggle.

### Backend changes (small)
Add to `kora_backend/core/urls.py` + a new view in `core/views.py`:

```
POST /api/valve/control/        # body: { "command": "open" | "close" }
GET  /api/valve/status/         # returns { "state": "open" | "closed", "last_changed_at": "..." }
```

These views authenticate the customer, look up their assigned device/asset, and
either (a) write a setpoint + log an operator action, or (b) call the MQTT
service. **This is a 1–2 view + 1 route PR on the backend; can be done in
parallel to the mobile app.**

### Mobile UI
- New "Valve" tab in the bottom nav (between Notifications and Settings), or
  a prominent card on the home screen. The home-screen card is recommended
  for v1 because it makes the feature immediately discoverable.
- Big circular toggle: green (open) / red (closed) with a confirmation modal
  before changing state. Lockout cooldown (5s) to prevent rapid toggling.
- Status history list below the toggle, pulled from operator action logs.

## 7. Setup From Zero (Windows)

> A complete `README.md` is included with the project. Quick version:

### Step 1 — Install Flutter SDK
1. Download Flutter stable from
   `https://docs.flutter.dev/get-started/install/windows`.
2. Extract to `C:\src\flutter` (avoid `C:\Program Files\` — needs write access).
3. Add `C:\src\flutter\bin` to `PATH`.
4. Run `flutter doctor` — install missing pieces (Android Studio, Xcode on
   macOS, Chrome for web).

### Step 2 — Clone & enter the project
The project is already at `C:\Users\eyu\Desktop\koracontrol\kora_mobile`.

### Step 3 — Generate platform folders
```
cd C:\Users\eyu\Desktop\koracontrol\kora_mobile
flutter create . --project-name kora_mobile --org com.koracontrol
```
This adds `android/`, `ios/`, `web/`, etc. without overwriting `lib/`.

### Step 4 — Configure env
Copy `.env.example` to `.env` and set:
```
KORA_API_BASE_URL=http://10.0.2.2:8000/api/      # Android emulator → host
# KORA_API_BASE_URL=http://localhost:8000/api/    # iOS sim or web
```
The `--dart-define=KORA_API_BASE_URL=...` flag is also supported at build time.

### Step 5 — Install dependencies
```
flutter pub get
```

### Step 6 — Run
```
flutter run                       # default device
flutter run -d chrome             # web
flutter run -d emulator-5554      # specific Android emulator
```

### Step 7 — Build release
```
flutter build apk --release                    # Android
flutter build appbundle --release              # Android (Play Store)
flutter build ios --release                    # iOS
```
